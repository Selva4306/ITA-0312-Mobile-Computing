# Task 6 – Design Challenge: RuralCare Field-Data Collection (13 Marks)

## Design assumptions

- The central service is reachable over HTTPS when a data connection exists; connectivity may disappear for several hours.
- A patient record contains identifying and health information and is therefore treated as highly sensitive.
- Devices are managed by RuralCare. Each enrolled device has a unique device identity and can be revoked by the server.
- Class C means either a J2ME-capable feature phone or a WML-only phone. These are not equivalent: J2ME can provide a small persistent application and Record Management Store (RMS); a WML browser generally cannot guarantee secure, durable offline record storage.
- The target is a ten-hour field shift, not continuous ten-hour network connectivity.

## Stage 1 – Interpret the problem (2 Marks)

### Input

1. Patient information entered by a field worker (patient identifier, observations, visit time, worker/device identity and consent status).
2. Device class and its runtime, storage, security and power capabilities.
3. Intermittent connectivity, server acknowledgements and possible interruptions during synchronisation.
4. Device events such as low battery, loss, restart, application termination and credential revocation.

### Output

- Locally saved patient records while offline.
- A server-side copy of every accepted record after connectivity returns.
- Acknowledgement/status for each record so the worker can distinguish pending, uploaded and rejected records.
- Audit information showing who created, changed and synchronised each record.

### Objective

Collect complete and accurate patient data during a ten-hour shift, protect it if a device is lost, and synchronise offline records later with **no silent loss and no duplicate logical records**.

### Constraints

- Workers may be offline for hours.
- All three device classes have different runtimes and security capabilities.
- The battery must last a ten-hour shift.
- Patient data must be protected at rest and in transit.
- Sync can be interrupted at any point.
- A WML-only browser may not offer reliable offline persistence or strong local cryptographic storage.

### Decisions

Choose the application strategy per device class, the amount of data stored locally, the encryption/key model, the power policy, the record identity and acknowledgement protocol, and the fallback for devices that cannot meet the minimum security requirements.

## Stage 2 – Propose the platform strategy (2 Marks)

**Selected strategy: a capability-based hybrid deployment.**

1. **Class A – Android:** Build a native Android application. Android provides an application sandbox, runtime permissions, Android Keystore, background-work scheduling, foreground services for visible active work, and mature offline database support. These mechanisms suit encrypted local records and controlled synchronisation.
2. **Class B – iPhone:** Build a native iOS application. iOS provides per-app sandboxing, Keychain, Data Protection, signed application distribution, background task facilities and URLSession networking. Native implementation uses the platform's own security and power rules rather than trying to imitate Android behaviour.
3. **Class C – J2ME:** Provide a small J2ME application only on tested devices that support persistent RMS storage and the required cryptographic implementation. Store the minimum necessary record fields, encrypt them at application level, and use a device-specific credential. Because older phones may lack a hardware-backed keystore, treat their local protection as weaker and use short retention, minimal identifiers and a PIN-derived key with rate limiting where feasible.
4. **Class C – WML-only:** Do **not** use a WML browser as the offline patient-record store. A browser-only WML client cannot be assumed to provide durable offline storage, a trustworthy private sandbox or secure key storage. Issue a managed smartphone/J2ME-capable device for offline sensitive capture. If WML access is retained, limit it to online, non-sensitive lookup or status functions.

### Why this principle fits the constraints

A single cross-platform codebase would not erase the major differences between Android/iOS security services and the limited J2ME/WML environment. Native clients can use each smartphone OS's strongest storage, permission and power mechanisms. A small J2ME client can support limited offline capture on devices that pass capability tests. WML-only devices are not falsely treated as secure offline computers. Restricting the WML role is a requirement-driven safety decision, not a preference for newer technology.

## Stage 3 – Critical information and constraints (2 Marks)

### Device capability table

|---|---|---|---|---|---|

| **C1: J2ME feature phone** | Java ME/MIDP application runtime | MIDlet permissions/signing vary by handset; application-level cryptography; limited device security; no assumed hardware-backed key store | Device-specific lifecycle and power controls; no reliable modern job scheduler; minimise radio use and keep processing brief | RMS record store, with application-level encryption and minimal retained fields; validate capacity and persistence on each model | Usually cellular data/SMS; protocol and TLS support vary by handset |
| **C2: WML-only feature phone** | WAP/WML browser, not a general app runtime | Browser/session controls vary; no assumed private durable store or strong key storage | Mostly browser/session-driven; little application control | No reliable secure offline patient-record store assumed | WAP/data session; generally online only |

### Information retained for safe offline synchronisation

| Retained item | Why it is required |
|---|---|
| Globally unique `record_id` (UUID) | Lets the server recognise a retry as the same logical record instead of inserting a duplicate. |
| `device_id` and `worker_id` | Establishes the source and supports audit, access control and device revocation. |
| `patient_ref` (pseudonymous local reference where possible) | Associates observations with the correct patient without unnecessarily repeating identity fields. |
| `created_at` and local sequence number | Preserves event order and helps detect gaps or clock anomalies. |
| Schema/version number | Allows the server to interpret records created by different app versions. |
| Payload and integrity/authentication data | Preserves the clinical observation and allows tampering or corruption to be detected. |
| Sync state and attempt metadata | Distinguishes pending, in-progress, acknowledged and rejected records after restart. |
| Server acknowledgement/receipt ID | Proves which records were durably accepted; prevents the client from deleting a record merely because it sent bytes. |
| Revision/version and conflict marker | Supports safe correction of an existing record without silently overwriting a newer server version. |

## Stage 4 – Complete solution specification (4 Marks)

The following is the implementation contract. Terms such as **MUST** indicate required behaviour.

### 4.1 Architecture by device class

| Layer | Class A – Android | Class B – iPhone | Class C – J2ME |
|---|---|---|---|
| Hardware | Smartphone CPU, flash, display, camera/sensors, cellular/Wi-Fi radio | iPhone CPU, flash, display, camera/sensors, cellular/Wi-Fi radio | Feature-phone CPU, limited flash/RAM, keypad/display, cellular radio |
| Kernel / OS | Linux kernel and Android system services | XNU kernel and iOS system services | Handset vendor OS and Java ME implementation |
| Runtime | ART | iOS native runtime | MIDP/CLDC Java ME virtual machine |
| Framework | Android SDK, Room, Keystore, WorkManager, FCM | Foundation/UIKit, Core Data, Keychain, BackgroundTasks, URLSession | MIDP APIs, RMS, tested cryptographic library and network APIs |
| App | RuralCare Field app | RuralCare Field app | RuralCare Lite MIDlet |

WML-only phones use a restricted web interface for non-sensitive online status/lookup only; they are not approved for offline patient capture.

### 4.2 Data capture and offline storage

1. The worker signs in using an individual account and device-bound credential. The app downloads only the assigned work list.
2. The client validates required fields locally and creates a UUID before saving a new visit.
3. The client writes the record to a durable local transaction before displaying **Saved offline**. A crash after this point must not erase the record.
4. Smartphone clients store records in private app storage using an encrypted database or encrypted record payloads. Encryption keys are generated/stored through Android Keystore or iOS Keychain/Data Protection-backed facilities; raw keys are never stored beside the database.
5. J2ME stores only the minimum required fields in RMS. Each record is encrypted before it is written. The app uses a device-specific secret and PIN-protected access; because the platform may not protect the key against offline extraction, the client must not cache bulk patient identity data. Devices that cannot implement and pass the required encryption and persistence tests are not enrolled for offline capture.
6. Each record has a local state: `PENDING`, `IN_FLIGHT`, `ACKNOWLEDGED` or `REJECTED`. The app never treats a successful socket write as server acceptance.
7. The app retains acknowledged records for a configured audit/retention period, then securely deletes local copies according to RuralCare policy.

### 4.3 Security specification

**Data at rest**
- Android: app-private files/database, encryption at rest, key material protected by Android Keystore.
- iOS: Data Protection-protected files/database and Keychain-held secrets.
- J2ME: application-level authenticated encryption before RMS storage, PIN-gated access, minimal data and short local retention. If the handset cannot safely protect the key or encrypted records, it is not approved for sensitive offline use.
- Do not write patient data, tokens or encryption keys to logs, shared storage, crash reports or notifications.

**Data in transit**
- Use HTTPS with TLS and normal certificate/hostname validation for smartphone clients.
- Use only a tested TLS-capable secure endpoint for J2ME. If a handset cannot establish a secure channel, do not send patient-identifiable data over plain HTTP. Use an approved secure gateway/protocol or replace the device.
- Authenticate each device and user. The server authorises the worker's assigned patients and records.

**Lost-device behaviour**
- The worker reports the loss through a separate channel. The server revokes that device's credentials and refresh tokens.
- Smartphone management applies remote lock/wipe where enrolled and supported. Local encryption protects data while the device is locked.
- J2ME credentials are revoked server-side; because remote wipe and strong hardware-backed storage cannot be assumed, local data is minimised and encrypted. The organisation must accept the residual risk of a legacy handset or stop assigning it sensitive offline work.
- A lost device must not be able to authenticate again after revocation. Already copied data cannot be remotely recalled; encryption and data minimisation reduce exposure.

### 4.4 Ten-hour power policy

| Condition | Client behaviour |
|---|---|
| Worker actively enters a visit | Keep screen/app active only during interaction; save each completed record immediately. |
| App in background while offline | Stop polling. Keep the encrypted queue durable. Use system-appropriate background execution only for short maintenance. |
| Waiting for connectivity | Use connectivity callbacks and exponential backoff with jitter; do not repeatedly wake the radio. |
| Sync available | Upload in bounded batches; release CPU/network resources after each batch. |
| Low battery | Defer optional downloads, map tiles, analytics and non-urgent sync; preserve data capture and local commits. |
| Shift complete | Perform sync when connected and on suitable power/network conditions; show unsent-record count before logout. |

The app must not hold a permanent wake lock or keep a continuous network connection. On Android/iOS, use platform background scheduling and upload facilities; on J2ME, sync on explicit user action or a detected available data session.

### 4.5 Synchronisation procedure

1. **Connect:** When network connectivity becomes available, the client establishes a validated TLS connection and authenticates the worker/device.
2. **Negotiate:** Client sends protocol version, schema version, device ID and the last acknowledged server cursor.
3. **Select:** Client selects records in creation/sequence order where state is `PENDING` or `IN_FLIGHT`. Each record keeps its original UUID across retries.
4. **Prepare batch:** Client marks the selected records `IN_FLIGHT` in a local transaction and sends a bounded batch. Every record includes its UUID, version, source device, timestamp and integrity/authentication data.
5. **Server validate:** Server authenticates the sender, authorises the patient/worker relationship, validates schema and integrity, and checks the UUID against a unique database constraint.
6. **Idempotent commit:** If the UUID is new, the server commits the record and receipt atomically. If it already exists with the same content, the server returns the original receipt without inserting another record. If the same UUID arrives with different content, the server rejects it for conflict review rather than overwriting silently.
7. **Acknowledge:** Server returns a per-record receipt for every committed or previously committed UUID. Client marks only those records `ACKNOWLEDGED` after validating the response and saving the receipt locally.
8. **Retry failures:** Unacknowledged records return to `PENDING` after timeout/restart. Retry with exponential backoff and jitter. Do not generate a new UUID for a retry.
9. **Conflict handling:** A rejected record remains on the device and is shown to the worker or supervisor for resolution. Corrections are new versioned revisions linked to the original record; the audit history is retained.
10. **Finish:** Client displays counts for acknowledged, pending and rejected records. It never deletes a pending record merely because an upload was attempted.

**Interrupted sync:** If the connection fails after the server commits but before the client receives the receipt, the client retries the same UUID. The server's unique constraint and idempotent response return the existing receipt, so no duplicate logical record is created. If the server did not commit, the retry inserts it once. Local state is reconciled only from server receipts.

### 4.6 Failure handling by device class

| Failure | Class A – Android | Class B – iPhone | Class C – J2ME |
|---|---|---|---|
| App/process terminated | Transactional local database preserves committed records; WorkManager resumes eligible sync | Durable local store preserves records; background task or next app launch resumes sync | RMS transaction/record write and explicit resume on next MIDlet launch |
| Battery exhausted | Recover from last local commit after charging/restart | Same; retain unsent queue | Same if RMS write completed; use small atomic record writes |
| Network drops mid-upload | Retry same UUID and reconcile receipts | Retry same UUID and reconcile receipts | Retry same UUID on next available data session |
| Device lost | Revoke token, remote lock/wipe if managed; encrypted app data | Revoke token, managed lock/wipe; Data Protection/Keychain | Revoke credentials; encrypted minimal local data; residual legacy-device risk |
| Storage full/corrupt | Stop accepting new records, show clear error, preserve/export recoverable queue; never silently overwrite | Same | Stop capture and alert worker; do not claim a record was saved if RMS write fails |
| Unsupported security/transport | Block enrolment until fixed | Block enrolment until fixed | Do not store/send identifiable records; replace device or restrict to non-sensitive online use |

## Stage 5 – Desk-check (1 Mark)

**Scenario:** A Class A worker is offline for six hours, battery falls to 20%, and the phone is lost before synchronisation.

| Step | State and decision | Data and protection outcome |
|---|---|---|
| 1 | Worker signs in. Device identity and user credentials are valid. | Only assigned patient references/work items are cached. |
| 2 | Worker goes offline. Each visit is validated, assigned a UUID and committed to the encrypted private database. | Records remain locally recoverable; sync state is `PENDING`. No server copy exists yet. |
| 3 | Six hours pass without connectivity. App performs no continuous polling and keeps the pending queue durable. | No record is lost merely because the phone is offline. |
| 4 | Battery reaches 20%. App reduces optional work and continues essential local capture. | Existing encrypted records remain; optional downloads and analytics are deferred. |
| 5 | Phone is lost before sync. Worker reports loss using another device/channel. | Server revokes the lost device's credentials. No sync acknowledgement exists, so the server correctly shows these records as not yet received. |
| 6 | Attacker attempts to inspect the locked phone. | App-private encrypted data and protected keys make direct offline reading harder. If the device is unlocked or compromised, exposure risk is higher; remote wipe may help only if the phone reconnects. |

**Result:**
- **Exposed:** Device metadata and any information visible outside the protected app boundary (for example, an overly descriptive notification, if the implementation made that mistake). The design therefore uses generic notifications.
- **Lost:** No server copy of the six-hour unsynchronised records exists at the moment of loss. If the device is destroyed or cannot be recovered, those locally held records may be unavailable; this is a residual risk of offline-first collection.
- **Recoverable:** If the device is recovered and its encrypted store is intact, the pending records can be synced after re-authentication. If the organisation has separately captured a legally approved paper/secondary record, it can be re-entered with audit linkage. The system must not falsely claim that unsynchronised records are on the server.

This trace shows that encryption protects confidentiality but cannot guarantee recovery of data that has never left a lost device. Operational procedures must therefore include prompt loss reporting and a controlled clinical fallback for critical visits.

## Stage 6 – Attack the design (2 Marks)

| Adverse condition and why it is challenging | Predicted behaviour before test | Trace / result after applying it |
|---|---|---|
| **1. A stolen phone is unlocked.** The attacker may already have access to the user's active session, so storage encryption alone is not enough. | App requires re-authentication for sensitive screens/exports, locks after inactivity, minimises cached patient identity and supports device revocation. | Attacker may see data currently visible in the active session until lock/revocation takes effect. Revocation blocks later server access but cannot erase data already viewed or copied. **Partial failure:** confidentiality cannot be guaranteed against an attacker holding an unlocked, active device. Refinement: short inactivity lock, step-up authentication for export, hidden notification content, and rapid loss reporting. |
| **2. Sync is corrupted or interrupted after server commit but before receipt.** The client cannot know whether the server committed the batch. | Client retains UUIDs and marks records acknowledged only after durable receipts. Server enforces UUID uniqueness and idempotency. | Client retries the same UUID. If committed, server returns the existing receipt; if not, it inserts the record. No duplicate logical record is created. **Survives**, provided server commit and UUID uniqueness are transactional. |
| **3. Class C phone has no secure key storage or cannot perform validated TLS.** Local encryption may be undermined if the key is stored beside the data, and network data may be exposed. | Capability check prevents sensitive offline enrolment on a device that cannot meet minimum cryptographic and transport requirements. | Test device fails enrolment for offline patient capture. It may use a WML page only for non-sensitive online status, or RuralCare supplies a supported J2ME/smartphone device. **Survives by refusing an unsafe capability**, but loses Class C offline capture on that model. This is an explicit compatibility limit, not a hidden security assumption. |
| **4. Worker edits a record after a prior version was synchronised.** Concurrent edits can overwrite newer clinical information. | Each revision has a version and parent record ID; server compares versions and rejects stale updates for review. | Server detects version mismatch and records a conflict instead of last-write-wins overwrite. Worker/supervisor resolves it with an auditable correction. **Survives** without silent data loss. |

### Critical decisions and remaining assumptions

- **Critical for no duplication:** stable UUID per logical record, idempotent server processing and a durable per-record acknowledgement.
- **Critical for confidentiality:** app-private encrypted storage and protected keys on smartphones; minimal encrypted data plus strict capability gating on legacy phones.
- **Critical for power:** durable local commits and event-driven/batched sync rather than continuous polling.
- **Assumption that fails:** It is not safe to assume every J2ME/WML handset provides secure storage, modern TLS or reliable background execution. The refined design explicitly tests J2ME devices and excludes WML-only devices from offline sensitive capture.
- **Residual risk:** No software can guarantee recovery of records that exist only on a physically lost or destroyed offline device. RuralCare must balance offline collection with a documented critical-data fallback and prompt device-loss reporting.

## Final design decision

RuralCare should deploy native, encrypted offline-first apps on Android and iOS; a constrained, tested J2ME client only where its cryptographic and persistence capabilities pass acceptance tests; and no offline sensitive-record workflow on WML-only phones. UUID-based idempotent synchronisation, server receipts, device revocation and power-aware batching address the central integrity, confidentiality and ten-hour battery requirements.
