# Assignment 4 — Q2
## Task 2: From Platform Requirement to Architectural Comparison (8 Marks)

**Scenario:** A secure messaging app must receive messages on Android, iOS and Windows while the screen is off, while protecting content, conserving battery and remaining responsive.

## 2.1 — Model the Requirement (2 Marks)

| Element | Model |
|---|---|
| Input | Android, iOS and Windows architecture: kernel, system interfaces, runtime, framework, process model, isolation, IPC and push services. |
| Output | A comparison matrix, message-delivery traces and a platform-specific background messaging design decision. |
| Objective | Determine how each architecture affects reliable, secure and battery-efficient message delivery when the app is not foregrounded. |
| Constraints | Screen off; app may be suspended or terminated; background execution limits; confidentiality and isolation; low battery use; low notification latency. |
| Decision | Choose the push and background-processing mechanism for each OS and decide which parts of the client can be shared versus platform-specific. |
| Required information | Kernel family and system-call boundary; driver/network path; push infrastructure; runtime and callback model; lifecycle/termination policy; sandbox and permissions; IPC; background quotas and power management. |

**Requirement interpretation:** Do not depend on a permanently running socket or service. Use the platform push service to alert/wake the app, then perform short permitted work. Keep message persistence and end-to-end encryption in the application protocol; send an opaque message ID rather than plaintext in the push payload.

## 2.2 — Hypothesis (1 Mark)

**Hypothesis:** Background process and wake-up policy will affect message delivery more than kernel family, because the OS decides whether a suspended or terminated app may be resumed for a push and how much execution time it receives.

## 2.3 — Comparison Matrix (3 Marks)

| Area | Android | iOS | Windows |
|---|---|---|---|
| Kernel family / structure | Linux monolithic kernel with loadable modules, drivers and Android changes; most framework services run in user space. | Darwin XNU hybrid kernel combining Mach facilities, BSD components and I/O Kit driver infrastructure. | Windows NT hybrid design with kernel-mode components, executive services and user-mode subsystems. |
| Kernel-level programming interface | Linux system calls and device interfaces; Binder driver supports Android IPC. Apps normally call framework APIs, not arbitrary syscalls. | Mach traps and Mach IPC plus BSD/POSIX system calls; I/O Kit supports drivers. Apps use public frameworks, not private kernel interfaces. | NT system-service boundary; Win32 is the supported app interface. Device access commonly uses I/O control requests (IOCTLs). |
| Runtime | Dalvik (historical) is a register-based VM executing DEX bytecode with interpretation and JIT. Android 5.0+ uses ART with JIT and AOT. | Objective-C runtime is a native language runtime, not a bytecode VM. App code is native ARM64; runtime supports class metadata and dynamic dispatch such as `objc_msgSend`. | WinRT is an API/metadata and language-projection system, not one universal VM. C# uses .NET; C++/WinRT is compiled to native code. |
| Application framework | Android SDK/framework: Activity and Service lifecycle, notifications, permissions, JobScheduler/WorkManager and FCM integration. | UIKit/SwiftUI, UserNotifications and BackgroundTasks; APNs and iOS lifecycle services manage remote notifications and app activation. | UWP/WinUI or Windows App SDK, WNS and background-task/lifecycle APIs. Exact facilities vary by UWP versus packaged WinUI/desktop app. |
| Isolation | Per-app Linux UID and process sandbox; SELinux mandatory access control; permissions gate protected APIs. | Code signing, per-app container and entitlements; privacy permissions restrict sensitive APIs. | AppContainer/package identity and declared capabilities restrict packaged apps; brokered APIs mediate access. |
| IPC | Binder driver/framework for system services; intents, bound services, broadcasts and content providers at higher level. | Mach ports/messages underneath; XPC and system frameworks provide higher-level IPC. | ALPC is used internally; apps commonly use COM/RPC, WinRT activation, named pipes and app services. |
| Background push | FCM, commonly through Google Play services. High-priority pushes can grant temporary background execution, subject to Doze and policy limits. | APNs via system push infrastructure. Eligible background pushes may wake/launch an app briefly; delivery is discretionary and can be throttled. | WNS. Raw push can trigger registered background work or wake a supported app model, subject to capability and lifecycle rules. |
| Consequence for messaging | Use FCM, persist messages server-side, process quickly in the callback/service and notify. Do not rely on an unrestricted background service/socket. | Use APNs alert pushes for user-visible urgency; silent pushes are best-effort refresh, not guaranteed immediate execution. | Use WNS and raw-push/background-task activation where supported; keep tasks short and account for app-model differences. |

### Design interpretation and decision

- **Android:** FCM is the primary wake-up/notification path. High priority can allow brief work; it does not authorize unlimited background execution.
- **iOS:** APNs alert notifications are suitable when immediate user awareness matters. Silent pushes may be delayed, coalesced or throttled.
- **Windows:** WNS raw notifications can activate background work in supported app models. Register the trigger and required capability; displaying a notification and running app code are distinct actions.

**Shared product design:** Keep message queueing, acknowledgements, encryption and retry logic in the app/server protocol. Implement small platform adapters for FCM, APNs and WNS. Send only an opaque message identifier in the push; authenticate, fetch and decrypt content locally.

## 2.4 — Desk-Check: Screen-Off Incoming Message (1 Mark)

Assume push registration is complete, the app has been launched before, the network is available and the app is suspended—not user force-quit.

### Android

1. **Network hardware:** Wi-Fi/cellular modem receives the FCM packet.
2. **Linux kernel/driver:** Network driver and kernel network stack process the packet and pass it to the relevant user-space service; power mechanisms permit required wake-up.
3. **Google Play services/FCM:** FCM routes the push to the app's registration token. High priority may temporarily allow background work.
4. **Android framework:** Resolves the target app and applies permission, background and power policy; starts its process/service if needed.
5. **ART/app process:** ART executes app code; `FirebaseMessagingService.onMessageReceived()` is invoked.
6. **Application callback:** Validate ID, fetch encrypted content if required, persist it, acknowledge it and post a notification; finish promptly.

### iOS

1. **Network hardware:** Wi-Fi/cellular hardware receives APNs traffic.
2. **Darwin kernel/driver:** XNU networking and driver layers process traffic for the system push infrastructure.
3. **System push service:** APNs connection is handled by the system push service (commonly apsd), which identifies the target app.
4. **iOS notification/lifecycle services:** An alert can be displayed by the OS without running app code. For an eligible background push, iOS may resume or launch the app in background.
5. **dyld/Objective-C runtime:** On a new process launch, dyld maps the executable and libraries and the runtime/frameworks initialize. A suspended in-memory process avoids full loading.
6. **Application callback:** With remote-notification background mode enabled, the app delegate receives `application(_:didReceiveRemoteNotification:fetchCompletionHandler:)`; it does limited work and calls the completion handler.

**Desk-check result:** Both systems can display a notification with the screen off without a permanent app socket. Neither guarantees that application code runs instantly: Android applies FCM priority and background limits; iOS treats silent pushes as discretionary and time-limited.

## 2.5 — Challenge: OS Terminates App for Memory Pressure (1 Mark)

**Changed condition:** The OS terminated the process to reclaim memory. This is not the same as the user force-quitting the app.

**1. Prediction:** Delivery behaviour will differ in timing and certainty. Android can recreate an app process for an eligible high-priority FCM message. iOS can relaunch an eligible app for a background remote notification, but delivery is discretionary and can be delayed or discarded. A visible alert may still be presented by the OS without an app callback.

**2. Responsible architecture:**
- Android: FCM/Google Play services, process manager/activity manager, background policy and the app's service entry point.
- iOS: APNs/system push service, iOS lifecycle manager, remote-notification capability and app delegate callback.

**3. Relevant trace and result:**

| Step | Android | iOS |
|---|---|---|
| Push arrives | FCM receives the push through Google Play services. | APNs push reaches system push service. |
| Process check | Android sees no process and evaluates message priority and background restrictions. | iOS evaluates push type, capability, app state and delivery policy. |
| Activation | An eligible high-priority FCM can cause process/service startup and callback. | An eligible background push can launch the app directly into background and deliver the callback. |
| Work | App performs short work, stores the message and posts a notification. | App gets limited time, processes the event and calls completion handler. |
| Restriction | Normal-priority pushes may be delayed by Doze. A force-stopped app is a different state and generally needs user action. | A user-force-quit app is not automatically launched for remote notifications until relaunched; silent pushes may be throttled/discarded. |

**Prediction check:** Correct. OS memory-pressure termination does not automatically block future push-triggered execution, but neither platform guarantees unrestricted or instantaneous work. The important distinction is OS termination versus user force-quit. Server-side persistence and later synchronization are essential.
