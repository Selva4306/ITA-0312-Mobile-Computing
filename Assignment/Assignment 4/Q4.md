# Task 4 – Security Forensics: SecureNotes (7 Marks)

## Platform selected

This repair uses **Android** as the reference platform. The relevant architecture is the Linux-kernel application sandbox, Android application framework and permission manager, Android Keystore, package installer/code-signing verification, and the TLS networking stack.

## 4.1 Locate the defects (2 Marks)

| Original decision | Security mechanism bypassed or unused | Why Android cannot protect the user if unchanged |
|---|---|---|
| Request every permission at installation for possible future use | Runtime permission model and least-privilege design | A permission grant gives the app authority to access the protected resource. Asking for unrelated permissions expands the damage possible after compromise and undermines informed consent. Android can enforce the granted permission boundary, but it cannot decide that an app's unnecessary request is inappropriate. |
| Save the login token in a file readable by other apps | Application sandboxing and secure storage | Android normally isolates each app's private internal storage using a distinct Linux UID. Placing the token in shared/external storage or another world-readable location deliberately moves it outside that private boundary. The OS cannot make a deliberately shared file private to SecureNotes. |
| Accept updates from any source without verifying the producer | Package code signing and update identity verification | Android package installation verifies APK signatures, and an installed app's update must be signed with the same signing identity (or a valid signing-key lineage). A custom updater that downloads and executes unverified code, scripts or plug-ins bypasses this trust decision. The OS cannot authenticate content that the app itself chooses to execute outside the normal package-update path. |
| Use plain, unencrypted server connections | Transport protection (TLS) and certificate validation | The network stack transports the bytes but does not automatically encrypt an app's HTTP traffic. Anyone able to observe or modify the network path can read credentials and alter responses. Android cannot provide TLS confidentiality or server authentication when the application deliberately uses cleartext HTTP. |

**Key distinction:** Android provides enforceable security boundaries, but application design determines whether sensitive data and operations remain inside those boundaries.

## 4.2 Construct an attack scenario (2 Marks)

**Scenario:** A worker connects SecureNotes to public café Wi-Fi. A malicious app is already installed and has ordinary access to shared files. The attacker also controls the café's access point.

1. SecureNotes writes its login token to a shared file. This is the first design error: the token is no longer protected by SecureNotes' private application sandbox.
2. The malicious app scans accessible shared storage and reads the token. **Confidentiality is first lost at this step**, when the token is read by an unauthorised app.
3. The worker opens SecureNotes and signs in over plain HTTP. The café attacker captures the request and can read the credentials or token in transit. This is a second independent confidentiality failure.
4. The attacker reuses the stolen token to impersonate the worker and retrieve private notes.
5. The attacker can also modify an unencrypted server response, for example replacing a saved note or changing a recovery link. **Integrity is lost when SecureNotes accepts the modified response as genuine.**

The malicious app and network attacker exploit two separate defects: shared token storage and missing TLS. The attack does not require breaking Android's sandbox; the application placed the token where another app could access it.

## 4.3 Repair the design with minimal changes (2 Marks)

| Defective decision | Minimal repair | Android mechanism and architectural location |
|---|---|---|
| Request every permission at install time | Remove permissions not needed by current features. Request a dangerous permission only when the user invokes the feature that needs it; explain the purpose and handle denial. | Android permission model in the framework/package manager, with runtime consent UI. For example, request `READ_CONTACTS` only when the user chooses contact import. |
| Store token in a shared file | Store the token in app-private internal storage, encrypted with a key protected by Android Keystore. Prefer short-lived access tokens and refresh-token rotation. Never put authentication secrets in shared/external storage or logs. | Linux UID sandbox protects private app files; Android Keystore provides app-scoped cryptographic key operations, with hardware-backed protection where available. |
| Accept updates from any source | Use the official package installation/update path. Verify the publisher and package signature; reject unsigned, incorrectly signed or unexpected update packages. Do not dynamically load executable code from an unauthenticated server. | Android package installer and package manager verify APK signing identity and update continuity. The app's own updater must not bypass that verification. |
| Use HTTP | Use HTTPS for every authenticated endpoint; validate the server certificate and hostname; disable cleartext traffic in the app's network security configuration. | Android networking/TLS stack and Network Security Configuration, above the kernel network transport. |

### Example Android configuration

The application should disable cleartext traffic in its manifest:

```xml
<application
    android:usesCleartextTraffic="false"
    ... >
</application>
```

A production app should also use a Network Security Configuration where appropriate, keep certificate validation enabled, and avoid custom trust managers that accept every certificate.

## 4.4 Regression check (1 Mark)

**Legitimate behaviour to preserve:** The user can import names from the phone's contacts after explicitly agreeing.

**Regression test:**

1. Install the repaired SecureNotes build. Confirm that it does not request contacts permission at first launch.
2. Open **Import from Contacts**. The app explains why it needs access and requests `READ_CONTACTS` at that point.
3. Grant permission. Confirm that the contact picker/import feature reads the permitted contacts and displays the selected names.
4. Deny permission in a second test. Confirm that notes, login and other features continue working and that the app offers a manual-entry alternative.
5. Inspect storage and network traffic: the token is absent from shared storage, and authenticated requests use HTTPS.

**Result:** Least-privilege permission handling preserves the consent-based contact feature. The repairs remove unnecessary authority and protect tokens, updates and network traffic without removing the application's legitimate function.

## Conclusion

The four defects are design failures, not missing magic features in Android. The repaired design deliberately uses the OS sandbox, runtime permission model, Keystore, package-signature verification and TLS rather than bypassing them.
