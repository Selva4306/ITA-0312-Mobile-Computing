# Task 5 – Power Management Reasoning (7 Marks)

## Platform context

The policy below uses Android as the example. Android's kernel power-management facilities, device drivers, sensor hardware and framework services cooperate to suspend the application processor when possible. The fitness app must not hold a permanent partial wake lock merely to avoid missing every sensor sample.

## 5.1 Design the power-state policy (3 Marks)

### State-transition table

| State | Hardware and kernel behaviour | Entry condition | Exit condition | Work allowed |
|---|---|---|---|---|
| **Active** | Display and application processor are on; CPU frequency scales with load; sensors and radios are enabled as needed. Kernel schedules foreground work normally. | User opens the app, starts a workout, interacts with the device, or a short processing task requires immediate execution. | Screen off and no immediate interaction; workload can be batched; or workout tracking moves to low-power monitoring. | Foreground UI, user-initiated work, sensor processing and short network operations. |
| **Idle / doze preparation** | Display is off; CPU can enter low-power idle states; framework defers non-urgent jobs and batches alarms/network work. Sensor hardware may continue sampling into its FIFO without waking the CPU for every sample. | Screen has been off for a period, device is stationary/unplugged, and no immediate user interaction is required. | User interaction, a permitted maintenance window, a significant motion event, or an urgent platform-delivered event. | Whitelisted/foreground services only for justified work; scheduled jobs and batched sensor delivery. Ordinary background polling is deferred. |
| **Suspended** | Kernel suspends most application-processor execution; devices enter low-power states; only configured wake sources (for example, power button, selected sensor interrupt or radio/modem event) can resume processing. | No runnable work remains and the system has prepared wake sources. No app holds a long-lived wake lock. | Hardware wake event, user interaction, or a platform event that is permitted to wake the device. | No ordinary app code. The kernel/firmware and designated wake-capable hardware remain able to signal an event. A short platform-authorised service may run after wake. |

**Transitions:** Active → Idle when the display turns off and immediate work ends. Idle → Suspended when queued work is drained and wake sources are configured. Suspended → Active on user interaction. Suspended → Idle after a short background event finishes. Idle → Active when the user returns or starts a workout.

### Fitness sampling policy

- Configure the sensor at the lowest sampling rate that still meets the workout's accuracy requirement.
- Use sensor batching/FIFO so the sensor can collect readings while the CPU sleeps; process a batch when the hardware buffer is near its limit or a suitable wake event occurs.
- Use a foreground service with a visible notification during an explicitly started workout if continuous tracking is a core user-visible feature.
- Acquire a partial wake lock only for a bounded operation that truly must keep the CPU running. Release it in a `finally` path and enforce a timeout.
- Do not poll sensors or the network continuously from a background loop.

This preserves the required sensor history without forcing the processor to remain awake for the whole shift.

## 5.2 Change the assumption: urgent push while suspended (2 Marks)

**Insufficient part of the original policy:** The Suspended state was described as allowing no ordinary application execution. That is correct for normal app code, but insufficient if the design assumes that no event can wake the device or that the app itself must remain awake to receive a message.

**Repair using Android push-based wake-up:**

1. The server sends an urgent, user-visible notification through Firebase Cloud Messaging (FCM) using high-priority delivery only for genuinely time-sensitive events.
2. The device's messaging infrastructure/radio receives the push and the platform wakes the device briefly as permitted.
3. Android dispatches the message to the app's messaging service. The app performs only short, bounded work: validate the message, save a small state change, and post a notification.
4. If longer work is needed, enqueue it with WorkManager/JobScheduler and let the system choose an appropriate execution window.
5. Return to idle/suspended operation after the brief work completes.

**What the application must stop doing:** It must stop holding a permanent partial wake lock, maintaining a polling socket, or running a tight background loop just to check for messages. It must not use high-priority pushes as a substitute for routine polling. FCM delivery can be delayed by network conditions and platform policy, so it is not a hard real-time guarantee; the server should retain urgent events until the client acknowledges them.

## 5.3 Change the requirement: Battery Saver at 15% (2 Marks)

When charge reaches 15%, Android Battery Saver is enabled (subject to the user's/system policy). The application detects the state using the power-management APIs and changes its own workload.

| Layer | Changes when Battery Saver activates |
|---|---|
| **Kernel / hardware** | The system favours lower power states and may reduce CPU performance, background activity and radio/display power use. Hardware continues only the sensor and wake functions required by the platform and active user-visible workout. |
| **Runtime / framework** | Background jobs, alarms and network access may be deferred or restricted by Android power policy. The runtime/framework exposes the power-save state so the app can adapt. |
| **Application** | Reduce optional sampling frequency where accuracy rules allow; batch sensor reads and uploads; stop animations and non-essential refreshes; postpone analytics, map prefetch and background sync; retain workout-critical measurements and save them locally. |

**User-visible trade-off:** The map may update less frequently and non-essential statistics may appear after the workout rather than immediately. This is acceptable because the essential function—recording the workout and preserving its readings—continues, while optional visual updates are delayed to help the device complete the ten-hour shift.

**Acceptance checks:** With the screen off, verify that sensor batches accumulate without a continuous CPU wake lock. Verify that a test urgent push wakes the device briefly and creates a notification. At 15% charge, verify that optional work is deferred but workout samples are retained.
