## Task 1: Architecture Review — Diagnose and Repair a Poor Architecture Description

**Chosen operating system: Android**

## Task 1.1 — Diagnose the Description (2 Marks)

The draft is incomplete because it names only a few broad concepts and does not define the interfaces, responsibilities, or control mechanisms needed to implement or evaluate the system.

1. **Important architectural layers are missing.** The note jumps from hardware to applications without identifying device drivers, the Hardware Abstraction Layer (HAL), native libraries, Android Runtime (ART), or framework services. Without these layers, an engineer cannot determine where hardware-specific code belongs or how applications access system capabilities.

2. **The kernel is assigned an incorrect responsibility.** Saying that the kernel “runs the applications” confuses application execution with resource and hardware management. Android uses the Linux kernel to manage processes and threads, memory, scheduling, device drivers, networking, security mechanisms, and system calls. Application code runs in user space, normally in an application process, with ART executing managed code.

3. **The runtime is not defined.** “Runtime” could refer to a language runtime, virtual machine, or execution environment. In Android, ART executes application DEX bytecode. It uses mechanisms such as interpretation, just-in-time (JIT) compilation, and ahead-of-time (AOT) compilation. The draft does not state what is executed or when translation occurs, so the application execution path cannot be evaluated.

4. **The permission and security model is vague.** Permissions are not simply switched on by an unspecified OS component. Apps declare permissions; the package manager records package and permission information; the user may grant or deny applicable runtime permissions; and framework services check access when protected operations are requested. The Linux kernel also enforces process isolation and security policy, including SELinux. The draft does not identify these enforcement points.

5. **Power management has no trigger or mechanism.** “Saves battery when needed” does not explain which component detects inactivity, low-power conditions, or system policy, nor what actions follow. Android framework power services coordinate with kernel power-management facilities and hardware-specific power interfaces to manage wake locks, suspend, CPU performance, and other power states.

6. **The application-to-OS communication boundary is missing.** The note does not explain how an app requests services. Android applications normally call framework APIs; framework services perform policy and permission checks and communicate with other processes through Binder IPC. Hardware access is mediated through system services, HAL interfaces, and kernel drivers rather than direct application access. Without this path, interfaces and trust boundaries are unclear.

## Task 1.2 — Repaired Android Layered Architecture Specification (3 Marks)

### Layered view

The following is a simplified logical view of Android. ART and native libraries are shown together because they are supporting components used by the framework and applications; they are not one single executable layer.

```text
+------------------------------------------------------+
| APPLICATIONS                                         |
| System apps and third-party apps                     |
+------------------------------------------------------+
                       |
             Framework APIs / Binder IPC
                       v
+------------------------------------------------------+
| ANDROID APPLICATION FRAMEWORK                        |
| Activity, Window, Package, Location, Notification,   |
| Power and other system services                      |
+------------------------------------------------------+
                       |
          Runtime and native interfaces
                       v
+---------------------------+--------------------------+
| ANDROID RUNTIME (ART)     | NATIVE C/C++ LIBRARIES   |
| DEX execution, core       | Media, graphics, SQLite, |
| libraries, JIT and AOT    | SSL, libc and others     |
+---------------------------+--------------------------+
                       |
                HAL interfaces
                       v
+------------------------------------------------------+
| HARDWARE ABSTRACTION LAYER (HAL)                     |
| Standard interfaces for camera, audio, sensors,     |
| Bluetooth and other hardware modules                 |
+------------------------------------------------------+
                       |
             Kernel drivers / system calls
                       v
+------------------------------------------------------+
| LINUX KERNEL                                         |
| Process and memory management, scheduling, drivers, |
| networking, security and low-level power management |
+------------------------------------------------------+
                       |
                       v
+------------------------------------------------------+
| PHYSICAL HARDWARE                                    |
| CPU, RAM, display, storage, camera, radio, sensors,  |
| battery and other device components                  |
+------------------------------------------------------+
```

### Layer specifications

| Layer | Responsibility | What it exposes to the layer above | What it depends on below |
|---|---|---|---|
| **1. Applications** | Provides user-facing functions such as calling, messaging, camera, and third-party app features. Each app runs in its own application process/sandbox under its assigned Linux UID. | User interface, app features, and requests to framework APIs. | Android framework APIs, ART, native APIs where permitted, and the application process environment. |
| **2. Android Application Framework** | Provides reusable high-level services and manages application lifecycle, windows, packages, notifications, locations, resources, and power policy. | Java/Kotlin API classes and system-service interfaces. | ART, native system components, Binder IPC, and lower system interfaces. |
| **3. Android Runtime (ART)** | Executes DEX bytecode and supplies core runtime libraries, memory management, and garbage collection. It may interpret code and use JIT and AOT compilation to translate bytecode into native machine code. | Runtime execution environment and core library functions to apps and framework code. | Linux process, memory, threading, and system-call facilities. |
| **3. Native C/C++ Libraries** | Supplies lower-level functions for graphics, media, databases, cryptography, and system operations. | Native APIs and libraries to framework components and, where available, apps through supported interfaces. | Linux system libraries, kernel interfaces, and relevant HAL implementations. |
| **4. Hardware Abstraction Layer (HAL)** | Hides device-specific hardware implementation details behind standard interfaces. HAL modules provide functions for components such as camera, audio, sensors, and Bluetooth. | Standard hardware-service interfaces to Android framework services. | Linux kernel drivers and the device hardware. |
| **5. Linux Kernel** | Manages CPU scheduling, processes, threads, virtual memory, device drivers, networking, low-level security enforcement, and kernel power operations. | System calls, device nodes, driver interfaces, and low-level services to user-space components and HAL implementations. | Physical CPU, memory, storage, buses, and peripheral hardware. |
| **6. Physical Hardware** | Performs computation, stores data, displays output, and provides connectivity and sensor functions. | Hardware resources and signals to kernel drivers. | Electrical power and the device's physical components. |

### Explicit placement of key components

- **Kernel:** The Linux kernel is below the HAL. It manages hardware resources, processes, memory, drivers, networking, and low-level security and power operations. It does not directly run the application user interface.
- **Runtime:** Android Runtime (ART) is in user space, alongside native libraries as a supporting execution layer. ART executes DEX bytecode. Depending on the app and execution state, code can be interpreted or compiled using JIT and AOT mechanisms.
- **Security enforcement:** Security is enforced at multiple points. The Package Manager maintains package and permission information; users grant or deny applicable runtime permissions; framework APIs and system services check permissions when protected operations are requested. The Linux kernel enforces per-app UID isolation and SELinux policy. Thus, security is not the responsibility of one layer alone.
- **Power management:** Android's framework power-management services, including PowerManagerService, coordinate system power policy in user space. They work with kernel power-management mechanisms and device-specific power interfaces to manage wake locks, suspend, CPU performance, and other power states.
- **Application-to-OS communication:** An app calls a framework API. The request is handled by framework code or a system service; cross-process service calls commonly use Binder IPC. The service applies relevant permission checks and, when hardware is required, accesses the appropriate HAL interface and kernel driver. Apps do not normally access hardware drivers directly.

## Task 1.3 — Design Defence (1 Mark)

The repaired specification is precise because it identifies each architectural layer, assigns it a defined technical responsibility, and states the interfaces it exposes and the dependencies it uses below. It also locates ART, the Linux kernel, security enforcement, and power management explicitly. The application-to-framework-to-service communication path, including Binder IPC and hardware mediation through HAL and kernel drivers, defines the system boundaries. These implementation-level details make the design testable and evaluable, unlike a general marketing description.
